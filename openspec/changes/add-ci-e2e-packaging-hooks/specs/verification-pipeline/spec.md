# Spec Delta

## Purpose

定义本地钩子与 CI 的分层验证契约：在提交、推送、PR 与打包四个时机分别验证什么，确保关键行为在接近用户环境的条件下被自动执行，失败能够阻断流程而不是依赖人工发现。

## ADDED Requirements

### Requirement: 钩子随依赖安装自动启用

项目 MUST 在开发者安装依赖后自动启用版本库自带的钩子，MUST NOT 要求每位开发者手动执行额外的安装或配置命令。

#### Scenario: 克隆后安装依赖

- **WHEN** 开发者克隆仓库并安装依赖
- **THEN** 提交前与推送前的钩子被安装到本地仓库
- **AND** 开发者无需再执行任何钩子初始化命令

#### Scenario: CI 中安装依赖

- **WHEN** CI 安装依赖
- **THEN** 钩子安装步骤不使安装失败，也不在 CI 中执行任何钩子

### Requirement: 提交前执行静态检查与单元测试

提交前钩子 MUST 执行类型检查、构建、测试夹具生成以及单元与协议测试，并在类型错误或单元测试失败时拒绝提交。它 MUST NOT 执行锁集成测试、端到端测试、依赖下载或启动图形界面，且 MUST 在常见开发机上于 30 秒内完成。

#### Scenario: 类型错误阻止提交

- **WHEN** 暂存内容存在类型错误且开发者执行提交
- **THEN** 提交被拒绝
- **AND** 输出指出错误的文件与位置

#### Scenario: 单元测试失败阻止提交

- **WHEN** 类型检查通过但任一单元或协议测试失败
- **THEN** 提交被拒绝
- **AND** 输出指出失败的测试

#### Scenario: 不运行集成与端到端验证

- **WHEN** 提交前钩子执行
- **THEN** 锁集成测试与端到端测试不运行
- **AND** 该过程不需要访问外网或图形界面

#### Scenario: 反馈时间有界

- **WHEN** 在基准开发机上执行提交前钩子
- **THEN** 全套检查在 30 秒内完成

### Requirement: 推送前执行完整的非 GUI 验证

推送前钩子 MUST 依次执行类型检查、构建、测试夹具生成、单元与协议测试、锁安全集成测试。任一步失败 MUST 拒绝推送。该钩子 MUST NOT 启动图形界面或下载 VS Code。

#### Scenario: 单元测试失败阻止推送

- **WHEN** 任一单元或协议测试失败且开发者执行推送
- **THEN** 推送被拒绝
- **AND** 输出指出失败的测试

#### Scenario: 锁集成测试失败阻止推送

- **WHEN** 锁安全集成测试失败
- **THEN** 推送被拒绝
- **AND** 输出指出是锁不变量相关的失败

#### Scenario: 不依赖图形环境

- **WHEN** 在没有图形界面、且无法访问外网的环境中执行推送前钩子
- **THEN** 验证仍能完成，不因缺少显示器或需要下载 VS Code 而失败

### Requirement: CI 在两个桌面平台验证核心行为

CI MUST 在 Windows 与 Ubuntu 上对每次推送到主分支和每个拉取请求执行类型检查、单元与协议测试、锁安全集成测试。任一平台失败 MUST 使整个工作流失败。

#### Scenario: 单个平台失败

- **WHEN** 一个平台通过而另一个平台失败
- **THEN** 工作流结论为失败
- **AND** 两个平台的日志都被保留以便对比

#### Scenario: 两个平台通过

- **WHEN** 两个平台的核心验证都通过
- **THEN** 工作流结论为成功
- **AND** 其结果可用作分支保护所要求的检查

### Requirement: CI 在真实 VS Code 宿主中验证扩展

CI MUST 在真实的 VS Code 扩展宿主中执行端到端验证，覆盖 Windows 与"无显示器但提供虚拟显示"的 Linux。端到端失败 MUST 使工作流失败，不得被静默忽略。

#### Scenario: 激活并浏览数据

- **WHEN** 端到端验证运行
- **THEN** 扩展被激活，四个命令均注册
- **AND** fixture 的 schema 与数据网格内容被成功加载

#### Scenario: 查看器打开期间外部写入

- **WHEN** 查看器已打开 fixture
- **THEN** 同一进程中的另一个 DuckDB 实例可以写入新行
- **AND** 刷新后新行出现在网格中

#### Scenario: 端到端失败不被忽略

- **WHEN** 端到端验证失败
- **THEN** 工作流结论为失败
- **AND** 失败原因可从该步骤日志定位

### Requirement: 发布物必须独立验证

CI MUST 为 win32-x64 与 linux-x64 构建目标平台专属的 vsix，解压后使用不依赖仓库工作目录的 Node 进程验证其中的 helper。验证 MUST 覆盖：helper 能启动并打开 fixture、能返回 schema、静止时打开句柄数为 0、dispose 成功。验证失败 MUST 使工作流失败。

#### Scenario: 打包缺少运行时依赖

- **WHEN** vsix 中缺少 helper 运行所需的原生绑定
- **THEN** 验证步骤失败并使工作流失败
- **AND** 日志指出 helper 启动或加载失败

#### Scenario: 打包产物可用

- **WHEN** 解压后的 helper 打开 fixture
- **THEN** schema 可读、静止时打开句柄数为 0、dispose 返回成功
- **AND** 该 vsix 作为工作流产物被保留

### Requirement: 本地与 CI 共享同一验证入口

提交前钩子、推送前钩子与 CI 核心验证 MUST 通过同一组项目脚本入口执行，使本地通过能够预测 CI 核心验证通过（环境差异除外）。

#### Scenario: 同一入口

- **WHEN** 任一本地钩子通过
- **THEN** CI 核心验证执行的是同一组脚本
- **AND** 不存在只在一处生效的额外检查步骤
