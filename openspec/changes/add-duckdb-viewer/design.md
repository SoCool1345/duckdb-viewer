# Design

## Context

见 `proposal.md` 的动机。当前仓库只有 Python 探测环境（`pyproject.toml` + `.venv`，DuckDB 1.5.6），没有任何扩展工程，因此本设计同时定义工程骨架。

锁的实测结果（Windows 10 / DuckDB 1.5.6，脚本见"验证"章节）决定了全部架构选择：

| 场景 | 结果 |
|---|---|
| 两个进程各持只读连接 | 允许 |
| 他进程持只读连接，本进程读写打开 | 失败，错误含 PID 与可执行文件名 |
| 他进程持读写连接，本进程只读打开 | 失败 |
| 他进程持读写连接，本进程复制文件 | Windows 上失败（强制性文件锁） |
| 库含未 checkpoint 的 WAL，只读打开 | 成功读到 WAL 中已提交数据，`.wal` 原样保留 |
| 数据库文件带只读属性，只读打开 | 成功，不需要目录写权限 |

单次操作成本（1M 行 / 3MB 测试库）：

| 方式 | 耗时 |
|---|---|
| 进程内 `open → 取一页 → close` | ~44ms（open 24ms + page 20ms） |
| 复用连接热查询 | ~14ms |
| 冷启动进程（解释器启动 + import + open） | ~480ms |

结论：**每次操作重建连接的成本可接受**，因此不需要为了性能而持有连接。这是整个设计的地基。

## Goals / Non-Goals

**Goals:**

- 让"静止时零句柄"成为结构性保证，而不是开发者记忆里的约定。
- 让锁冲突成为可解释、可恢复的界面状态。
- 让宿主异常退出不会留下占锁进程。
- 让上述性质可以被自动化测试卡住。

**Non-Goals:**

- 不追求毫秒级翻页（接受每次操作 ~50ms 的连接开销）。
- 不做写入、编辑、SQL 控制台。
- 不实现跨查询的一致快照（放弃"第 1 页与第 2 页来自同一时刻"的语义）。
- 不做 DuckDB 扩展的自动安装。

## Decisions

### D1. 只读自定义编辑器（`CustomReadonlyEditorProvider`）

`.duckdb` / `.ddb` 注册为自定义编辑器，`priority: "option"`，`supportsMultipleEditorsPerDocument: false`。

- 用 readonly provider 而不是普通 provider：文件不可保存、不可编辑，`save` 语义天然不存在，避免"用户以为 Ctrl+S 会写库"的误解。
- 禁止同文档多编辑器：一个文件对应一个标签页，消除"两个面板指向同一文件、谁在占锁"的歧义。
- `option` 而非 `default`：不劫持双击。用户在设置里可切换为默认。

替代方案：Tree + 面板（多文件时归属混乱）、命令 + 虚拟文档（不像工具）。已否决。

### D2. 独立 Node 助手进程承载 DuckDB

```
+-------------------- 扩展宿主 (TypeScript) --------------------+
|  custom editor  <--postMessage-->  webview (网格/schema树)     |
|        |                                                       |
|        +-- DbSession（每文件一个）                             |
|              锁状态机 / 串行队列 / 取消 / 变更指纹             |
+------------------------------|---------------------------------+
                               | JSON-RPC over stdio
+------------------------------v---------------------------------+
|  helper (node, @duckdb/node-api)                               |
|   - 静止时 0 个 DatabaseHandle                                 |
|   - open(ACCESS_MODE READ_ONLY) -> execute -> close             |
|   - stdin EOF / 心跳超时 -> exit                                |
+----------------------------------------------------------------+
```

理由：

- 锁归属清晰：占锁的是助手，不是 VS Code；可以整进程终止，释放确定性最高。
- 崩溃隔离：原生绑定崩溃只损失助手。
- 可以在进程边界上强制"无状态"：助手没有 session 概念，每次请求自带 `dbPath`。

替代方案与否决理由：

| 方案 | 否决理由 |
|---|---|
| 原生绑定放在扩展宿主内 | 宿主直接占锁；崩溃会带走整个扩展宿主；无法整进程强杀 |
| Python 助手 | 发布要求用户装 Python，或 PyInstaller 打包 50MB+；与"装插件即用"冲突 |
| 外部 `duckdb` CLI | 依赖用户预装；嵌套类型/BLOB 只能退化为文本；版本易与库不匹配 |
| 读取时复制文件 | Windows 上写者持锁时复制失败；Unix 上会得到撕裂快照 |
| duckdb-wasm | webview 无可靠通道读取任意本地 `.duckdb`，且存储版本常滞后 |

### D3. 每次操作新建连接，绝不缓存连接

请求粒度为"一次读操作"，助手内执行 `open → prepare/execute/fetch → close`，`finally` 中关连接。没有连接池，没有 keep-alive。

- 静止时助手持有的 `DuckDBInstance` 数量必须为 0，这是可断言的不变量，由 `status` 请求暴露。
- 若未来要加 `holdLockMs`，只能作为"操作间保持 X 毫秒"的显式开关，默认 0，且必须让状态栏可见。v1 不实现。

按实测 44ms/次，翻页、排序、过滤各一次请求，交互上可接受。

### D4. 单助手进程 + 按 dbPath 串行队列

全局一个助手进程，多个数据库标签页共享。每个 `dbPath` 一个先进先出队列，队列内串行，避免同一文件并发连接造成自锁与不确定的错误信息。

- 跨文件可以并行（默认并发上限 2），防止一个大库拖住所有面板。
- 不按库分进程：锁不是持有型的，进程隔离收益低、进程数量与内存开销高。

### D5. 协议：stdio 上的 JSON-RPC，请求自带路径与超时

```
-> { id, method: "openSession" | "listSchema" | "fetchPage" | "interrupt" | "status" | "dispose", params }
<- { id, ok: true, result } | { id, ok: false, error: { code, message, detail } }
<- { event: "ready" | "handleDelta", ... }   // 通知，无 id
```

要点：

- 请求必须自带 `dbPath`，助手不保存"当前数据库"这种状态 —— 状态越少，越不会偷偷持有句柄。
- `error.code` 采用固定枚举（`LOCKED`、`VERSION_TOO_NEW`、`CORRUPT`、`TIMEOUT`、`CANCELLED`、`SQL_ERROR`），界面文案由扩展侧决定，助手只报事实。
- `fetchPage` 的返回必须包含 `changed: { mtimeMs, size }` 指纹，供界面判断"外部已修改"。
- 所有单元格在助手侧就转成显示字符串（见 D7），JSON 传输不需要 BigInt 的特殊处理。
- `status` 返回 `{ openHandles: n, files: [] }`，测试与"诊断"命令直接消费它。

### D6. 孤儿防护：stdin EOF 为主，心跳为兜底

```
宿主死亡 --> 管道关闭 --> helper stdin 'end' --> process.exit(0)
宿主卡死 --> 3s 无 ping --> helper 自杀
```

- 助手不监听网络端口，不写 PID 文件；生命周期完全由父进程管道绑定。
- 扩展侧 `deactivate` 先发 `dispose`，再 `kill`，最后等退出（有超时）。
- 宿主被强杀时无法执行 `deactivate`，此时只有管道 EOF 一条防线，因此它必须是主防线而不是"补充"。
- 取消/超时会先标记请求为已取消：还在队列里的请求在开始执行前直接跳过，不打开数据库；已经开始执行的请求被中断。
- 如果中断后 5 秒内核仍不归还句柄，助手直接退出（最后手段）。助手是可再生资源，留锁不可接受。
- 关闭标签页等同"取消 + 销毁"：中断活动请求，并让所有异步续作在统一请求入口处停止，不再产生新查询。
- 宿主侧的 pending 请求按助手进程实例归属：旧实例退出只清理它自己的请求，不会误伤刚启动的新实例。

### D7. 类型在助手侧归一化为显示字符串

DuckDB 的 `DECIMAL`/`HUGEINT`/`BLOB`/嵌套类型经 JSON 传输容易失真，因此：

| 类型 | 呈现 |
|---|---|
| DECIMAL / HUGEINT / UUID | 完整文本，禁止转 JS number |
| STRUCT / LIST / MAP / ARRAY | 结构化文本（JSON 风格），保留嵌套可读性 |
| BLOB | `长度 + 截断预览`，不整块传输 |
| TIMESTAMP / DATE / TIME | 保留原始的完整精度文本，不用本地化格式覆盖 |
| NULL | 单独标记，与空字符串区分 |

实现上优先在 SQL 层做 `::VARCHAR` 或 `to_json` 的形式转换，避免每个类型在 TS 侧写转换分支。代价是失去数值排序能力 —— 但排序在服务端完成（D8），不受影响。

### D8. 排序/过滤/分页全部下推到 SQL

- 排序与过滤不进内存，直接生成 `ORDER BY` / `WHERE`；标识符用双引号转义，拒绝把用户输入拼进非值位置。
- 分页优先 `ORDER BY rowid` 的键集分页（若对象有 rowid）；否则退回 `LIMIT/OFFSET` 并在界面标注"顺序不保证稳定"。
- 行数只显示 `duckdb_tables().estimated_size` 概算；精确 `count(*)` 不在 v1（大表可能耗时且占锁窗口变长）。
- 元数据用一次请求批量取：`duckdb_tables()`、`duckdb_columns()`、`duckdb_views()`、`duckdb_constraints()`，展开树不再连库。

### D9. 变更检测用文件指纹，而不是跨查询事务

每次响应带 `(mtimeMs, size)`；与上次不同即认为外部已写入，界面出现横幅与刷新按钮。

- 明确不提供"跨页一致快照"：那需要长事务或长连接，与锁目标直接冲突。
- 指纹可能漏检（同一秒内同尺寸变更），因此界面文案用"数据可能已变化"，而不是断言"数据已变化"。

### D10. 冲突与错误的用户可见映射

| 助手错误 | 界面行为 |
|---|---|
| `LOCKED` | 解析 PID/进程名 → "被 python.exe (58504) 占用" + 重试 / 等待释放（1s 探测，可取消） |
| `VERSION_TOO_NEW` | 说明版本不兼容，引导升级查看器；绝不尝试改写文件 |
| `CORRUPT` / I/O | 展示原因与"重试"，标签页保持可用 |
| `TIMEOUT` | 说明因超时被放弃，句柄已释放 |
| `CANCELLED` | 静默恢复界面，不弹错误 |

### D11. webview 采用原生 TS + 服务端分页的 DOM 表格

- 不用前端框架：状态量小（schema、当前表、页码、排序、过滤），减少构建与依赖面。
- 每页固定行数（默认 100，可配），DOM 表格足够；不做无限滚动，避免"滚动即连库"的连续占锁窗口。
- 样式使用 VS Code 主题变量，CSP 使用 nonce，不加载外部资源。

### D12. 工程骨架与依赖

- TypeScript + esbuild：扩展入口与 webview 各自打包；`target: node20`。
- 依赖：`@duckdb/node-api` 固定 `1.5.6-r.2`（与用户环境 DuckDB 1.5.6 对齐，避开 2.0 RC）。
- 助手作为独立 bundle 打包，扩展通过 `process.execPath` + `ELECTRON_RUN_AS_NODE` 或内置 node 启动，确保用户无需安装 Node。
- 测试：`vitest` 覆盖协议与 SQL 生成；集成测试用第二个 node 进程以读写方式打开同一库，作为"外部写入者"。

## Risks / Trade-offs

- **`@duckdb/node-api` 版本线**：1.5.6-r.2 是 r 系列，非正式 stable；2.0 线目前是 RC。→ 固定 1.5.6-r.2，升级作为独立任务，并在 `VERSION_TOO_NEW` 路径上给出清晰指引。
- **存储版本只进不退**：用户库若被更新的 DuckDB 写过，本查看器打不开。→ 不改写、不降级、明确报错；DuckDB 升级后同步升插件。
- **长查询占锁窗口**：`count(*)` 或大表全扫期间，外部写入仍会失败。→ 取消 + 超时（默认 20s）+ 不提供"全表扫描"按钮；v1 只做分页读取。
- **Windows 强制锁导致无退路**：写者持锁时无法复制文件，因此没有"快照兜底"。→ 不做假承诺，直接在 UI 说明这是 DuckDB 的并发模型。
- **网络盘/SMB 上锁语义不可靠**：DuckDB 官方也提示共享目录风险。→ v1 不做特殊处理，文档标注。
- **原生二进制被杀软/EDR 拦截**：会导致助手无法启动。→ 启动失败时给出可操作错误，而不是静默失败。
- **`GEOMETRY`/`VARIANT` 等类型依赖扩展**：未加载扩展时某些列无法渲染。→ 渲染失败退化为"该类型需要扩展"的占位说明，不影响其他列。
- **webview 大单元格**：单行超大文本可能拖垮渲染。→ 助手侧截断到固定字节数，提供"查看完整值"再单独取。
- **指纹漏检**：见 D9。→ 文案用"可能"，并提供手动刷新。

## Migration Plan

无既有用户与已发布版本，属于首版：

1. 建立扩展工程骨架与构建脚本，`F5` 可启动调试宿主。
2. 实现助手与协议，先让 `status` / `listSchema` 在测试中跑通。
3. 接入自定义编辑器与 webview，完成"打开 → 看 schema → 看一页数据"。
4. 补齐排序、过滤、变更提示、锁冲突流程。
5. 添加锁不变量集成测试并纳入 CI。

回滚：卸载扩展即可，无迁移数据、无写入路径，对用户数据库零副作用。

## Verification

锁行为已用 Python + DuckDB 1.5.6 在 Windows 上实测（临时脚本，不入库）：

- 只读持锁 → 外部读写打开失败，错误文本含 PID。
- 读写持锁 → 外部只读打开失败、文件复制失败。
- 只读打开含 WAL 的库 → 读到已提交数据，`.wal` 未被 checkpoint。
- 连接/页查询/重连耗时分别为 24ms / 20ms / 44ms。

集成测试将用 node 进程复现同样的场景，作为 CI 门禁（见 `tasks.md`）。
